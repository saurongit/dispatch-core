# Архитектура

**Русский** | [English](ARCHITECTURE.md)

## Стабильный центр, заменяемые границы

```text
 ГЕНЕРАТОРЫ ЗАЯВОК                  РОЛЕВЫЕ ИНТЕРФЕЙСЫ МЕССЕНДЖЕРОВ
 сайт | ввод по телефону | API | бот       Telegram | MAX
          |                                      |
          v                                      v
 +------------------- долговечный вход / FastAPI -----------------+
 | аутентификация | дедупликация провайдера | callback-capability |
 +-------------------------------+---------------------------------+
                                 v
 +------------------------- прикладной слой -----------------------+
 | команды | unit of work | identity | read models | идемпотентность |
 +-------------------------------+---------------------------------+
                                 v
 +------------------------- доменное ядро -------------------------+
 | WorkOrder | политики пула | evidence | TrackingSession | события |
 +-------------------------------+---------------------------------+
                                 v
 +--------------------------- PostgreSQL ---------------------------+
 | агрегаты | inbox/cursor | outbox | callbacks | исходящая очередь |
 +-------------------------------+---------------------------------+
                                 v
                         доставка в Telegram / MAX
```

Ни один адаптер провайдера не записывает данные напрямую в доменные таблицы.
Callback Telegram, кнопка MAX и HTTP-запрос проходят через один прикладной
сервис и одинаковые доменные инварианты. Интерфейсы клиента, оператора, мастера
и администратора находятся во frontend мессенджеров. Администратор через тот же
контур создаёт черновик IndustryPack, проверяет его и публикует конфигурацию
сервиса.

Поведенческая основа — `dez_core_dr`. Отраслевые пакеты обобщают его
терминологию, поля и требования к подтверждению работы, но не заменяют
проверенные сценарии клиента, оператора, мастера и администратора.

## Конфигурация и версии IndustryPack

В организации назначается один администратор-владелец. Это продуктовый
инвариант, поэтому в конфигураторе нет совместного редактирования, разрешения
конфликтов и согласования между несколькими администраторами. Один владелец
может одновременно иметь роли оператора и мастера; его конфигурационные сессии
при этом изолированы по Telegram/MAX и не перезаписывают друг друга.

Администратор без изменения кода настраивает бренд, каталог и порядок услуг,
одиночный или множественный выбор, типизированные поля (включая списки), тексты
вопросов, требования к закрытию, политику пула и названия ролей в карточках.
Изменения сначала живут в единственном черновике. Публикация архивирует прежнюю
активную версию и атомарно активирует черновик. Архивную или активную версию
можно скопировать в новый черновик, проверить и опубликовать вручную; прямого
непроверенного отката active-состояния нет.

При старте клиентского intake номер активной версии сохраняется в долговечной
сессии. Все последующие шаги читают именно эту active/archived-ревизию, поэтому
публикация администратором не меняет каталог, поля или evidence посреди уже
начатой заявки. Номер версии также записывается в детали созданной заявки.

## Политики распределения работ

`curated` сохраняет модель с участием диспетчера:

1. Заявка публикуется в пуле.
2. Исполнители нажимают «Готов взять»; каждый ответ сохраняется как
   `interested`.
3. Ни один ответ сам по себе не назначает заявку.
4. Координатор видит кандидатов и осознанно выбирает одного.
5. Остальные ответы получают состояние `rejected`, а выбранный — `selected`.

`first_claim` — явная альтернатива. Побеждает первая транзакция, которая
заблокировала заявку и успешно зафиксировалась. Прямое назначение работает без
публикации в пуле. Координатора можно прикрепить, но он не является обязательным
участником агрегата.

В PostgreSQL также есть частичный уникальный индекс, который запрещает одному
исполнителю иметь две активные заявки в одной организации. Этот инвариант
сохраняется при нескольких процессах API или воркеров и не может быть обойдён
гонкой в Python.

## Границы транзакций и доставки

```text
POST/poll провайдера
      |
      +-- транзакция: исходное inbox-событие + polling cursor
      v
входящий воркер
      |
      +-- транзакция: изменение агрегата + доменный outbox
      +-- долговечный дедуплицированный ответ
      v
проектор outbox
      |
      +-- транзакция: capability-токены + исходящие сообщения + отметка проекции
      v
отправитель -- сетевой вызов --> провайдер
      |
      +-- доставлено, повтор с backoff или dead letter
```

Модель доставки — at-least-once. Идентификаторы событий провайдера, версии
агрегатов, ключи идемпотентности, capability-токены и ключи дедупликации
исходящих сообщений делают повторение безопасным на значимых границах.
Callback-обработчики распознают уже зафиксированное целевое состояние, поэтому
сбой между фиксацией команды и завершением inbox не повторяет бизнес-эффект.

Захват выполняется через `FOR UPDATE SKIP LOCKED`. Строка, оставленная в
`processing`, снова становится доступной после stale-интервала. Для каждого
неуспешного элемента очереди действует ограниченный exponential backoff, а
после настроенного числа попыток он переходит в dead-letter состояние.

## Агрегаты

### WorkOrder

Хранит организацию, тип и источник заявки, определённые отраслевым пакетом
детали, необязательного заявителя и координатора, состояние пула, назначенного
исполнителя, требования к подтверждению, итоговый отчёт и optimistic version.
Каждый переход проверяет допустимое предыдущее состояние и участника.

### TrackingSession

Трекинг отделён от заявки, потому что маршрут может содержать множество точек.
Точка хранит время фиксации, время приёма, источник провайдера и необязательную
точность. PostgreSQL только добавляет новые точки; запись новой геопозиции не
удаляет и не переписывает предыдущую историю. Один активный tracking session на
заявку обеспечивается частичным уникальным индексом.

Каждая активная сессия владеет двумя независимыми 256-битными bearer-capability.
Клиентская capability читает только безопасную проекцию последней точки;
capability мастера может добавлять GPS-точки из браузера, но не читать
клиентское представление. Токены находятся во fragment URL, передаются API
только в заголовках и атомарно очищаются при завершении или отмене заявки.
Нативная геопозиция Telegram/MAX остаётся основным путём; `/track/share` —
независимый от провайдера браузерный резерв.

Получение адреса — отдельный capability-сценарий. После номера телефона intake
FSM предлагает клиенту нативную геопозицию мессенджера, ручной ввод и
одноразовую карту `/address#…`. Браузер передаёт токен только в заголовке. Одна
транзакция PostgreSQL блокирует соответствующую intake-сессию, сохраняет
координаты объекта, переводит FSM к услугам и удаляет токен. Точка обслуживания
копируется в детали заявки только после подтверждения и затем доступна
безопасной tracking-проекции; геолокация по IP не используется.

### Capability, участники и привязки

Payload кнопок мессенджера содержит непрозрачные истекающие токены, а не
доверенные роли или команды заявки. База разрешает токен только в пределах его
организации и роли. Production-участник представляет одного человека и может
иметь несколько явных членств в `actor_roles`, а также контролируемые привязки
Telegram и MAX. Канал или frontend бота выбирает действующую роль для текущего
взаимодействия, но не выдаёт эту роль.

Так поддерживается необязательный nano-пресет, в котором один владелец является
администратором, оператором и мастером. Удаление одного членства сохраняет
участника, остальные роли, привязки и историю. Общий staff-бот MAX просит
участника с несколькими ролями выбрать текущий режим; отдельные ролевые боты
Telegram определяют его по frontend.

Входящая идентичность включает `organization_id + provider + consumer_key +
external_event_id`. Поэтому клиентский и служебный боты могут получить
одинаковый ID события провайдера, не дедуплицируя и не перехватывая события друг
друга. Та же граница маршрутизации применяется к polling cursor и исходящим
очередям. Осознанное исключение на выходе — MAX staff sender: через один
физический токен он забирает сообщения `staff`, `admin`, `operator` и `master`,
но никогда `client`.

Неизвестная учётная запись оператора или мастера сначала попадает в долговечную
сессию до аутентификации. `/start` открывает 15-минутное окно с пятью
неуспешными попытками. Выданный администратором четырёхзначный код погашается,
только если активное членство совпадает с ролью выбранного frontend.
Несоответствие отклоняется до изменения внешней идентичности или членства.
Успешная привязка очищает одноразовый код и сессию до аутентификации; одинаковый
сценарий разбирают транспорты Telegram и MAX.

Состояние сценария оператора ограничено организацией, участником, действующей
ролью и провайдером. Поэтому admin-сценарий настройки nano-владельца,
операторский сценарий Telegram и операторский сценарий MAX не перезаписывают
друг друга. Создание мастера использует долговечный ключ запроса, защищённый
advisory lock PostgreSQL и уникальным индексом, поэтому повтор входящего события
не создаёт второго участника.

## Модель масштабирования

Разворачиваемый модуль — модульный монолит. Это сохраняет доступную стоимость
установки, транзакций, резервного копирования и отладки, одновременно оставляя
границы для выделения компонентов:

- все операционные строки содержат `organization_id`;
- обработчики команд зависят от портов unit of work;
- длинная история GPS изолирована и append-only;
- уведомления покидают транзакцию через outbox;
- несколько потребителей координируются блокировками базы;
- транспорты зависят от независимого от провайдера контракта;
- отраслевые пакеты являются данными, а не форками исходного кода.

Если измеренная нагрузка этого потребует, приём трекинга, доставка провайдеру и
публичная граница могут быть выделены без изменения модели WorkOrder. Заранее
они не разделяются.

## Профили развёртывания

```text
Текущий сервер: API + worker + PostgreSQL на VPS/сервере заказчика
Будущий desktop: то же ядро + локальная долговечная БД на офисном компьютере
Будущий hybrid:  офисное ядро/данные + небольшая публичная долговечная граница
```

Для polling Telegram не нужен публичный входящий порт. Документация MAX
рекомендует webhook для production, поэтому публичный HTTPS endpoint — целевой
серверный профиль MAX. Профили — варианты упаковки, а не форки продукта.

## Инварианты безопасности

- токены ботов, webhook-секреты и данные прокси никогда не попадают в Git;
- размер тела webhook ограничен, запросы аутентифицируются секретами провайдера;
- admin API keys сравниваются за постоянное время и должны содержать не менее
  32 символов;
- контейнеры приложения работают под фиксированным непривилегированным
  пользователем, в read-only режиме и без Linux capabilities;
- чтение между организациями и разрешение токенов ограничиваются в SQL;
- привязка сотрудников ограничена по времени, попыткам, роли и frontend;
- события провайдера долговечно изолированы по организации и логическому
  frontend;
- сетевые вызовы никогда не удерживают транзакцию базы открытой;
- геопозиция не принимается без активной tracking-сессии;
- клиентская capability чтения и capability мастера для записи трекинга
  различаются, ограничены по частоте и отзываются при каждом терминальном
  переходе;
- пригодность для регулируемой отрасли не заявляется без отдельной проверки
  соответствия и модели угроз.
