# Эксплуатация

**Русский** | [English](OPERATIONS.md)

## Конфигурация

Скопируйте `.env.example` в `.env`. Сгенерируйте независимые случайные значения
для пароля PostgreSQL, ключа admin API, секрета подписи callback и секрета
токенов исполнителя. Используйте URL-safe пароль PostgreSQL из букв, цифр или
hex-символов, потому что Compose подставляет его в URI подключения. Не
используйте токен бота как webhook- или admin-секрет.

Базовый `compose.yaml` запускает PostgreSQL, API и worker с отключёнными
приёмниками мессенджеров. `compose.transports.example.yaml` — пример override;
фактический override и файлы токенов должны оставаться приватными.

```bash
docker compose up --build -d
docker compose ps
curl http://127.0.0.1:8080/health/live
curl http://127.0.0.1:8080/health/ready
```

`/health/live` подтверждает только то, что процесс API отвечает.
`/health/ready` дополнительно проверяет PostgreSQL. У контейнеров worker есть
отдельный healthcheck на основе heartbeat в базе, поэтому запущенный, но
зависший worker получает состояние unhealthy.

## Адрес клиента, трекинг и GPS мастера

Задайте `DISPATCH_PUBLIC_BASE_URL` равным доступному извне origin, например
`https://dispatch.example`. Для передачи GPS в рабочей среде требуется HTTPS;
обычный HTTP допустим только при локальной разработке.

После шага с телефоном клиентский intake предлагает три варианта адреса:
нативную геопозицию мессенджера, одноразовую карту `/address#…` или ручной ввод.
Начальную область карты задают `DISPATCH_DEFAULT_MAP_LATITUDE`,
`DISPATCH_DEFAULT_MAP_LONGITUDE` и `DISPATCH_DEFAULT_MAP_ZOOM`. Сохранение точки
атомарно продвигает долговечную intake-сессию и погашает токен; клиент
возвращается в бот и нажимает «Продолжить после карты». Страница не определяет
геопозицию по IP. VPN обычно не меняет GPS, но клиенту с подменой геопозиции или
находящемуся не на объекте следует выбрать точку на карте либо ввести адрес
вручную.

При начале выезда worker отправляет клиенту read-only ссылку `/track#…`, а
мастеру — нативный запрос геопозиции мессенджера и резервную ссылку
`/track/share#…`. Просмотр и отправка используют разные случайные capability.
Fragment не передаётся в начальном HTTP-запросе; JavaScript отправляет его
same-origin API в заголовке. Завершение или отмена заявки очищает оба токена в
той же транзакции, что и терминальное состояние.

Опубликуйте через TLS reverse proxy маршруты `/address`, `/track`,
`/track/share`, `/v1/public/intake/location`, `/v1/public/tracking` и
`/v1/public/location`. Не переносите fragments в query parameters и не
записывайте capability-заголовки в access log.
На карте показывается обязательная атрибуция OpenStreetMap. Публичный растровый
сервис OSM не имеет SLA и может запретить коммерческий доступ; до появления
существенного платного трафика используйте подходящего провайдера или
собственные тайлы.

## Настройка сервиса в admin-боте

Для организации назначается один администратор-владелец. В Telegram разделы
доступны через меню команд: `/brand`, `/services`, `/fields`, `/evidence`,
`/allocation`, `/role_labels`, `/versions`, `/operators`, `/preview` и
`/publish`. В MAX те же действия доступны кнопками общего staff-бота после
выбора роли администратора.

Конфигуратор создаёт единственный черновик и не меняет активный клиентский flow
до `/publish`. Раздел `/versions` позволяет отменить неопубликованный черновик
или скопировать активную/архивную версию в черновик. Восстановленная версия
всегда требует предпросмотра и явной публикации. Уже начатые клиентские заявки
остаются на той версии формы, с которой были открыты.

## Регистрация участников

В штатном сценарии мессенджера копировать внешний ID не требуется.
Реализованный admin-сценарий создаёт оператора и возвращает короткоживущий
четырёхзначный код; оператор открывает правильного ролевого бота Telegram или
общего staff-бота MAX, нажимает `/start` и вводит код. В рабочем месте оператора
он может создать мастера, указав имя и телефон; мастер привязывается по
полученному коду через мастерского бота Telegram или того же staff-бота MAX.
Код одноразовый, ограничен frontend и защищён 15-минутной сессией ввода с пятью
попытками. Повтор последнего сообщения создания использует тот же долговечный
ключ запроса и не создаёт дубликат мастера.

Admin API остаётся полезным для фикстур разработки:

```bash
curl -X POST http://127.0.0.1:8080/v1/actors \
  -H 'Authorization: Bearer YOUR_ADMIN_KEY' \
  -H 'Content-Type: application/json' \
  -d '{
    "actor_id": "executor-1",
    "role": "master",
    "display_name": "Executor One",
    "provider": "telegram",
    "external_user_id": "123456789"
  }'
```

Доступные роли: `admin`, `operator`, `master` и `client`. Один участник может
иметь несколько явно назначенных ролей и отдельные привязки Telegram/MAX.

## Создание заявки

Каждый запрос создания требует стабильный `Idempotency-Key`. Повтор с тем же
ключом и телом возвращает ту же заявку; использование ключа с другим телом
возвращает `409`.

```bash
curl -X POST http://127.0.0.1:8080/v1/orders \
  -H 'Authorization: Bearer YOUR_ADMIN_KEY' \
  -H 'Idempotency-Key: customer-request-2026-0001' \
  -H 'Content-Type: application/json' \
  -d '{
    "work_type": "lift_repair",
    "source": "phone",
    "requester_id": "resident-7",
    "details": {
      "summary": "Lift stopped",
      "address": "Demo street 7",
      "asset": "lift-42"
    },
    "evidence": {
      "minimum_photos": 1,
      "comment_required": true
    }
  }'
```

API возвращает ID заявки. В локальной среде разработки задайте
`DISPATCH_ENVIRONMENT=development`, чтобы включить `/docs` со схемами пула,
назначения, трекинга, завершения и отмены. В рабочей среде маршруты `/docs`,
`/redoc` и `/openapi.json` отключены.

## Telegram

Для polling не нужен публичный endpoint. Задайте
`TELEGRAM_RECEIVE_MODE=polling`, подключите файл токена и запустите transport
override.

Для режима webhook опубликуйте `https://YOUR_DOMAIN/webhooks/telegram` через
доверенный TLS reverse proxy, задайте случайный `TELEGRAM_WEBHOOK_SECRET` и
зарегистрируйте URL методом Telegram `setWebhook` с тем же `secret_token`.
Telegram polling и webhook не могут работать одновременно.

## MAX

Поддерживаемая топология содержит ровно два логических frontend MAX на
организацию:

- `client`: публичный клиентский бот;
- `staff`: один общий бот для администратора, оператора и мастера.

При `bot_started` или `/start` staff-бот очищает предыдущий режим и показывает
только роли, которые сейчас выданы участнику. Его worker обрабатывает
уведомления всех служебных ролей, но не может забрать клиентскую очередь.
Пример Compose override запускает обоих MAX-ботов в режиме polling, поэтому ему
не нужен публичный callback endpoint и он не может смешать их события.

Адаптер использует `https://platform-api2.max.ru` и передаёт токен бота в
заголовке `Authorization`. Если установка выбирает webhook, опубликуйте
отдельный публичный URL для каждого физического бота и направьте каждый URL в
экземпляр frontend с соответствующим consumer key `client` или `staff`. Каждый
экземпляр публикует собственный обработчик `/webhooks/max` на HTTPS-порту 443.
Создайте подписку каждого бота с соответствующими URL и секретом:

```bash
curl -X POST https://platform-api2.max.ru/subscriptions \
  -H 'Authorization: YOUR_MAX_BOT_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
    "url": "https://MAX_CLIENT_OR_STAFF_DOMAIN/webhooks/max",
    "update_types": ["message_created", "message_callback", "bot_started"],
    "secret": "YOUR_MAX_WEBHOOK_SECRET"
  }'
```

MAX передаёт этот секрет как `X-Max-Bot-Api-Secret`; API сравнивает его до
сохранения события. Текущие требования MAX разрешают только HTTPS на порту 443
с доверенным сертификатом и рекомендуют webhook для рабочей среды. Подписка
webhook и long polling не могут работать одновременно.

## Обратный прокси-сервер и публикация

Compose напрямую публикует API для разработки. В рабочей среде разместите его за
поддерживаемым TLS reverse proxy, опубликуйте только необходимые маршруты,
ограничьте частоту запросов к admin API и по возможности закройте его сетью или
VPN. Если установка должна принимать переданный IP клиента, задайте
`DISPATCH_TRUSTED_PROXY_IPS` точным списком IP-адресов или CIDR прокси. Пустое
значение означает, что forwarding headers не считаются доверенными. Сохраняйте
rate limiting на границе, несмотря на наличие ограниченной локальной защиты от
злоупотреблений в приложении.

## Резервное копирование и восстановление

База данных — источник истины системы. Создайте и проверьте локальный дамп:

```bash
scripts/backup-database.sh /secure/local/dispatch-backups
scripts/verify-database-backup.sh \
  /secure/local/dispatch-backups/dispatch_YYYYMMDDTHHMMSSZ.dump
```

Первая команда создаёт дамп custom format через сервис PostgreSQL в Compose,
проверяет структуру архива и создаёт sidecar SHA-256. Вторая проверяет checksum
и выполняет реальное восстановление во временном, изолированном от сети
контейнере PostgreSQL. Она никогда не восстанавливает данные в рабочую базу.
В эксплуатационный регламент также должны входить:

- зашифрованные резервные копии PostgreSQL вне основного сервера;
- график хранения, соответствующий метаданным заявок, GPS и подтверждений;
- проверка восстановления в изолированную базу;
- отдельное резервное копирование конфигурации развёртывания без смешивания
  секретов в открытом виде с обычными архивами;
- проверка возможности ротации токенов ботов и webhook-секретов.

Compose создаёт volume `dispatch-postgres`, но сам по себе volume не является
резервной копией. Копируйте проверенные дампы в зашифрованное внешнее хранилище,
оповещайте о пропущенных запусках и регулярно репетируйте восстановление.

## Восстановление очередей

Строки inbox, outbox и исходящих сообщений имеют состояния `pending`,
`processing`, `delivered` или `dead`. Завершение worker после захвата задачи не
теряет её: stale-строки `processing` снова становятся доступными. Повторяющиеся
ошибки используют ограниченный backoff и в итоге переходят в `dead`.

Worker пишет ошибку при наличии dead-letter элементов и предупреждает, если
возраст работы в `pending` или `processing` превышает
`DISPATCH_QUEUE_WARNING_AGE_SECONDS`. Приведённый ниже аутентифицированный
endpoint возвращает количества по состояниям, самые старые timestamps и
heartbeat воркеров для настроенной организации:

```bash
curl https://dispatch.example/v1/operations/queues \
  -H 'Authorization: Bearer YOUR_ADMIN_KEY'
```

Успешные технические записи inbox/outbox/outbound удаляются ограниченными
пакетами после `DISPATCH_QUEUE_RETENTION_DAYS` (по умолчанию 30 дней). Также
удаляются истёкшие ключи идемпотентности и достаточно старые callbacks. Эта
задача обслуживания никогда не удаляет dead-letter строки, заявки, отчёты и
историю GPS; проверяйте и возвращайте dead-элементы в очередь только по
аудируемой процедуре.
